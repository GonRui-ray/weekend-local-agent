# 周末盲盒策划师｜项目介绍与产品规划

## 项目介绍

周末盲盒策划师面向有同城社交与休闲需求的本地居民，围绕“这周末和谁、去哪儿、怎么安排”提供决策支持。产品目标是把多人的空闲时间、出发地、预算和兴趣，整合为 2–3 套可以比较的附近路线，并生成便于发起邀约的邀请函。

产品以“信息整合 → 条件匹配 → 路线比较 → 发起邀请”为核心流程。AI 负责理解需求与辅助追问，信息工具提供活动和地点依据，程序校验时间、预算与通勤约束，前端通过固定 JSON 展示路线、费用、来源与邀请函。

发展路径采用“聚焦居民场景 → 建立单城活动供给 → 完善可执行路线 → 小规模试点 → 按质量扩城”。首版聚焦同城、同一天、1–6 人的安排，覆盖看展、餐饮与轻休闲；服务边界为查信息、排路线和生成邀请文案，交易与代发消息不纳入首版。

## 用户场景与核心价值

| 用户任务 | 产品设计 | 预期价值 |
| --- | --- | --- |
| 想在附近发现新鲜事 | 根据常住片区、兴趣、通勤上限和排除地点组织候选 | 提供适合居民日常生活的选择 |
| 朋友时间与预算不同 | 汇总各人的起点、空闲时段和预算口径，缺关键条件时追问 | 减少反复协调 |
| 信息散落在多个平台 | 将活动公告、地点信息与社区线索统一整理，保留来源 | 减少跨平台查找与核对成本 |
| 看了推荐仍难行动 | 提供可比较路线、时间线、集合点、费用预留和邀请函 | 缩短从“有兴趣”到“发起邀约”的路径 |

## 信息接入与供给建设

首轮供给建设选择一个城市、少量相邻片区，以看展和餐饮场景为切入点。城市根据活动来源可获得性、维护成本和用户招募资源确定；后续以同一套数据标准扩展。

| 数据层 | 计划来源 | 建设重点 |
| --- | --- | --- |
| 活动事实 | 场馆、主办方、官方文化资讯、授权活动 feed | 获取日期、场次、场馆、费用和预约说明；保留原始链接与更新时间 |
| 地点与交通 | 高德等地图服务 | 对齐起点与场馆的 POI、地址和坐标；接入站间与各人往返交通时间 |
| 发现与偏好 | 小红书及本地生活公开可检索页面 | 发现主题与小众地点；事实字段回到主办方或场馆来源核验 |
| 商业信息补充 | 经授权的本地生活与票务接口 | 按覆盖需求补充营业、评分、价格与场次，统一通过适配层接入 |

供给处理流程规划为：**采集 → 字段标准化 → 城市与日期过滤 → 去重与场馆匹配 → 来源核验 → 进入候选池 → 更新与失效处理**。

统一记录活动 ID、城市、类型、场馆、日期与场次、价格、预约要求、来源 URL、发布方和更新时间。对价格缺失、来源冲突与场次不明设置独立状态；活动到期退出候选，出行前重新检查关键字段。结构化供给先采用可核验公告或授权清单，验证覆盖后再增加自动采集渠道。数据结构见 [信息接入与整合](../信息接入与整合.md)。

## Agent 工作流规划

| 环节 | 关键设计 | 交付结果 |
| --- | --- | --- |
| 条件收集 | 对话与表单结合，提取常住地、各人时间与起点、预算、兴趣和距离；对歧义追问 | 可确认、可修改的需求结构 |
| 检索与整合 | 按城市、日期和偏好读取活动与地点，记录每个渠道的状态 | 有来源与有效期的候选池 |
| 排程与筛选 | 先检查共同时间、预算、活动时段和交通，再比较兴趣匹配与路线差异 | 目标 2–3 套路线；不足时如实返回 |
| 过程与结果展示 | 状态卡片反映实际工具执行；用固定 JSON 和 Schema 驱动界面 | 可比较卡片、时间线、费用与来源详情 |
| 邀约与反馈 | 邀请函随选中路线生成；记录修改原因和自愿出行反馈 | 邀约行动出口与下一轮优化依据 |

异常恢复与主流程一起设计：接口失败保留条件并提供重试；无匹配结果建议调整条件；来源不完整标明待确认；样例仅由用户主动选择。预算、时间与通勤由程序校验，模型输出通过 Schema 校验后再展示。

## 产品路线图与阶段交付

路线图按阶段验收推进，每个阶段明确目标、交付物和进入下一阶段的条件。

| 阶段 | 阶段目标 | 关键交付物 | 验收重点 |
| --- | --- | --- | --- |
| 第一阶段：居民场景与交互验证 | 确定高频需求和首版流程 | 5–8 位目标居民的探索性访谈与样例任务测试；场景优先级；手机交互问题清单；MVP 需求文档 | 形成可追踪的需求依据，明确输入、比较与邀请环节的障碍，并完成关键交互修订 |
| 第二阶段：单城活动供给 | 建立有来源、可更新的活动基础 | 城市与片区供给清单；统一字段；地图 / 搜索 / feed 适配；更新和失效规则；人工核验样本集 | 活动关键字段可追溯，异城、过期与重复记录能被过滤；按片区、日期与兴趣检查覆盖缺口 |
| 第三阶段：真实规划链路 | 将供给转化为可执行路线 | 云后端与真实工具调用；场次和交通校验；灵活站数；方案差异；来源展示与故障恢复 | 非样例请求能完成“输入—规划—邀请”；人工核对预算、时段和往返；无结果、故障和换城市可恢复 |
| 第四阶段：小规模居民试点 | 评估使用价值与运行成本 | 手机真机与弱网验证；关键埋点；试点反馈；质量与成本看板 | 根据有效规划完成率、活动核验通过率、耗时、修改原因和调用成本确定优化优先级 |
| 第五阶段：按质量扩展 | 复用供给标准与验证方法 | 新城市接入清单；渠道评估规范；城市覆盖与质量对比；分享功能优先级 | 逐城检查供给维护、路线质量和服务成本，达到试点验收标准后再扩大范围 |

其中，单城供给建设是后续排程、真实试点与扩城的基础；产品迭代优先级依次为活动可信、路线可行、方案有差异、手机操作顺畅。图片邀请卡、日历导出和朋友独立填写条件作为体验扩展，根据试点反馈排序。

## 评估与迭代机制

| 评估维度 | 计划观察的指标 | 用于什么决策 |
| --- | --- | --- |
| 流程完成 | 条件填写完成率、有效规划完成率、选路线与邀请函复制情况 | 优化输入、比较和邀约流程 |
| 内容与路线质量 | 来源字段覆盖率、活动核验通过率、过期率、硬约束违规率、路线地点重合度 | 优化供给、核验和排程 |
| 体验与成本 | 首次有效方案耗时、中位数与 P95 延迟、追问轮数、工具错误率、单次成功规划成本 | 优化调用顺序、等待体验和运行成本 |
| 持续价值 | 修改原因、实际出行自愿回访、再次规划情况 | 判断场景价值与功能扩展优先级 |

“有效规划完成率”按服务范围内、条件完整的会话计算：至少一套方案通过硬约束检查、被用户选中并生成邀请函才计为完成。试点先建立基线，再确定优化目标；样例任务、真实规划和实际出行分别记录。
