# 周末盲盒策划师｜项目介绍与后续计划

更新日期：2026-10-27。当前为产品 Demo，暂不推进 Python 云后端部署。

## 项目介绍

> 周末盲盒策划师是一个面向本地居民的 AI 产品 Demo，想解决朋友安排周末时信息分散、条件难协调、推荐难落地的问题。目标是把各人的时间、起点、预算和兴趣，整合成两到三套附近路线，再生成可以直接复制的邀请函。
>
> 目前已完成手机与桌面的样例交互，以及 Agent 后端、工具适配和结构化输出框架；可以体验路线比较、时间线与邀请函。真实活动 API 和云后端尚未接通，因此当前展示内容为明确标注的样例，不提供按所在地实时推荐。
>
> 现阶段先用 Demo 验证居民需求与操作流程。后续从一个城市接入可核验活动供给和地图服务，再部署后端、核对路线可执行性，最后开展小规模真实试点，根据任务结果和数据质量决定是否扩城。

## 当前能体验什么

[打开公开 Demo](https://gonrui-ray.github.io/weekend-local-agent/) → 主动点击「先拆一个样例盲盒」→ 比较三套路线 → 查看详情时间线 → 生成并复制邀请函。支持手机响应式布局及 JSON 导出。

首页不默认杭州；可以填写自己的常住城市。杭州仅为主动选择的固定产品样例，不代表杭州当周活动，也不会在其他城市检索失败时自动冒充当地推荐。当前静态页面不执行真实活动搜索、定位查询或按自然语言动态重排。

后端已包含需求理解与追问、会话条件、地图 / 搜索 / 活动 feed 适配、约束排程、SSE 状态、固定 JSON 与 Schema、异常降级。**代码与受控测试完成，不等于真实服务已上线。** 目前是一个可选协调模型加程序工具，执行角色标签不代表多个独立大模型。

首版边界为查信息、排路线和生成邀请文案。订票、订位、支付及自动向朋友发消息不在范围内。

## 为什么现阶段保留为 Demo

当前先验证三件事：本地居民是否需要这一工作流、两三套路线是否容易比较，以及邀请函是否有助于发起邀约。这些问题可先通过样例任务测试发现交互障碍；测试尚未开展，不能预先宣称用户认可或效率提升。

真实推荐还需要平台授权与服务凭证、云服务运行、持续更新的活动供给，以及活动日期、场馆、时间、费用和交通的真实核验。部署前端或获得一个搜索结果，都不能替代这些验证。现在暂不推进后端部署，相关技术配置保留为后续预案。

## 信息接入的后续思路

| 信息来源 | 负责解决的问题 | 接入原则 |
| --- | --- | --- |
| 主办方、场馆、官方文化资讯、授权活动 feed | 本周末有什么、在哪里、何时有效 | 保留原始 URL、日期、发布方、价格与预约说明，持续检查失效记录 |
| 高德等地图服务 | 起点与场馆匹配、位置和交通 | 常住地由用户确认；先做单城，后续补真实交通，POI 不能充当活动证明 |
| 小红书及本地生活公开可检索页面 | 发现地点、主题与偏好线索 | 当前未实时接通；公开摘要不能直接证明展期、票价、评分或库存 |
| 经授权的本地生活或票务接口 | 更完整的营业、评分、场次等 | 取得可用授权后经统一数据适配层接入；不以平台名称冒充已建立合作 |

数据先统一字段，再按城市、日期过滤、去重、匹配场馆，最后进入排程与排序。输出保留来源与核验状态；找不到就明确说明，不编造活动或用异城样例补齐。细节见 [信息接入与整合](../信息接入与整合.md)。

## 分阶段计划

| 阶段 | 要做的事 | 判断是否完成 |
| --- | --- | --- |
| 现在：Demo 验证 | 计划邀请 5–8 位目标居民做探索性访谈和样例任务；检查手机输入、方案比较与复制；记录反馈 | 用户理解样例边界并能完成操作，形成可追踪的需求与交互问题清单 |
| 后续一：单城实接 | 选一个城市与少量片区，整理官方或授权活动记录，接地图 / 搜索，部署后端 | 真实调用有记录，来源与活动日期可核验；无结果、故障和换城市可恢复 |
| 后续二：可执行性 | 补场次、营业时段、真实交通、灵活站数与方案差异 | 人工核验真实案例；时间、预算、往返与通勤符合约束 |
| 后续三：小规模试点 | 补真机、弱网、必要埋点及自愿回访 | 用有效规划完成率、活动核验通过率、耗时、调用成本和修改原因决定迭代 |
| 验证后再扩展 | 扩城市与渠道，评估图片邀请卡、日历及朋友独立填条件 | 有需求、供给质量与维护成本的证据，再扩大范围 |

以上为计划，未承诺上线时间。样例任务成功率不能代表真实规划成功率；邀请函被复制也不等于实际出行。

- 没有已验证的用户转化、留存或商业效果数据。
