# 周末盲盒策划师 · 云端本地生活版

面向**住在当地的人**。用户确认常住城市和片区，提供每个人日常出发地、空闲时间、预算、兴趣和不想再去的地方。先整合活动与生活资讯，再生成 1–3 条附近路线与邀请函。目标为 2–3 条；可行方案不足时如实返回。

延续参考 [教育 Agent](https://github.com/julikaalice-ux/edu-agent-learning-coach) 的 React + TypeScript 双场景、FastAPI SSE `/turn`、Gradio 云端入口及 JSON 校验结构。发布目标是一个公网 HTTPS 地址。此目录是待发布代码，**不代表已经上线**。

## GitHub 建设与展示

完整源码将由 GitHub 管理。仓库提供自动测试、前端构建、ModelScope 产物、GitHub Pages 展示工作流与 Docker / Render 云端运行入口。参见 [GitHub部署.md](GitHub部署.md)。Pages 未配置云接口时明确使用产品展示模式，只有主动选择的静态样例；配置公开云接口地址后可运行完整本地活动 Agent。模型与检索凭证始终放在后端保密变量。

## 发布到 ModelScope

`weekend-agent-modelscope.zip` 是扁平上传包；解压后 `app.py` 在根目录。源码中也可运行：

```bash
python3 scripts/build_space.py
```

在你的 ModelScope 账号新建独立的 Gradio 创空间，将 `build/modelscope/` 的全部内容放入空间根目录。入口 `app.py`，如需启动命令则为 `python app.py`，Python 3.12，端口 7860。运行时绑定 `0.0.0.0`，Gradio 容器在 `/`，React 在 `/ui-app/`。无需额外前端主机或访问用户电脑。

在平台保密变量中设置：

| 变量 | 用途 |
| --- | --- |
| `AMAP_KEY` | 真实多城市推荐必需，高德 Web 服务 Key，定位、逆地理编码、POI 检索 |
| `TAVILY_KEY` | 公开网页发现：官方文化信息、本地生活资讯、小红书可公开检索页面 |
| `EVENT_FEED_URL` | 可选，活动供给网关 HTTPS URL，返回统一活动 JSON；与搜索可并用 |
| `EVENT_FEED_TOKEN` | 可选，供给接口 Bearer 凭证，只存在服务端 |
| `EVENT_FEED_PATH` | 可选，平台内上传的活动 JSON 路径，适合授权导出或人工维护；与 URL 二选一 |
| `MODEL_API_KEY` | 可选，启用协调模型；未配置时是范围明确的规则理解 |
| `MODEL_BASE_URL` | 默认 `https://api-inference.modelscope.cn/v1` |
| `MODEL_NAME` | 默认 `Qwen/Qwen3-32B`，按账号实际可用 ID 调整 |
| `HOST` / `PORT` | `0.0.0.0` / `7860` |

真实演示至少需要**地图 + 一个有数据的信息源**。仅上传代码或填写空的活动模板不能得到真实活动。当前没有可用的平台发布授权或服务凭证，尚未发布或完成真实 API 联调。

部署后检查 `/health`（进程健康）、`/config`（Gradio）、`/ready`（所需服务是否配置）。`/ready` 在缺地图或缺活动来源时返回 503；配置检查不代表实际 API 已成功，真实状态按每轮来源卡显示。云平台健康检查应使用 `/health`，避免尚未配置凭证时反复重启。

包内也提供 Dockerfile：在打包目录构建镜像，运行时映射 7860 端口并注入同样的保密变量。多实例部署需要粘性会话或将内存会话替换为共享存储；本 Demo 按单实例运行。

## 从所在地到常住地

首页不预设任何城市。用户手动填写常住城市和片区，或点击「用当前位置」授权浏览器定位。后端通过高德将浏览器 GPS 坐标转换为地图坐标，再识别城市、区，**仍需用户确认是否为常住地**。不会用云服务器 IP 识别用户位置。

只把城市、片区写入本次需求，不用设备精确坐标冒充住宅地址。每个人的日常出发地仍由本人填写，可用附近地铁站；以这些起点做集合与往返估算。支持中国大陆城市，地图服务查不到的位置会提示调整，不能保证每个城市每种偏好都有足够的活动。

新增居民约束：单程通勤上限 30 / 45 / 60 分钟；排除最多 10 个去过且不想再去的地方；路线内部移动上限。默认不搜索一日游和游客集散点。更换城市时清空旧城市出发地与路线。普通检索缺配置、失败或无匹配时，保留当地条件并提示，**不自动切换杭州样例**。产品样例仅在设置页主动选择，始终标明不是所在地推荐。

## 活动与生活资讯摄入

完整流程与供给格式见 [信息接入与整合.md](信息接入与整合.md)。

1. 先拉取当前城市、出行日有效的结构化活动供给；校验字段、日期、URL，过滤异城、过期、重复和错误记录。
2. 并行搜索官方文化资讯、本地生活公开资讯与小红书公开可检索页面。搜索摘要保存为线索，不从摘要编造票价或展期。
3. 用高德确认日常出发地和场馆。供给记录里的活动场馆能引入新的候选起点，再找附近餐饮、咖啡或公共空间。
4. 在排路线之前，对齐最多 9 个地点的资讯，按 URL 去重，保留原链接、来源类型、发布与检索时间。供给票价一致时进入费用预留；冲突时按较高金额预留并显示冲突。
5. 校验预算、共同时间、步行、各人通勤、返程与排除地点。先按日期活动供给的匹配程度排序，再看可用线索与最慢通勤，输出最多 3 条不同起点的路线。

有来源信息会影响候选与排序。只有 POI 数据时，如实展示「周边地点路线」，不称为已查到本周末活动。每个资讯渠道展示取得匹配、无匹配、未配置或故障状态。

小红书 / 大众点评 / 美团 / 大麦等平台当前使用的是**公开搜索发现**。未宣称已获得它们的完整内容 API、评分或实时库存。拿到商业授权或现有数据服务后，可经统一供给网关接入，不需要重写路线器。未实现绕过登录、反爬或搬运完整笔记。平台官方、商家原始活动公告适合做事实来源；社区内容适合做偏好与发现线索。

## 固定输入输出与执行过程

`POST /turn` 请求示例见 `example-resident-request.json`。可对话，也可用明确条件表单。缺少信息会追问，后续可以修改条件或选择路线生成邀请函。

SSE 依次返回真实的 `progress` 事件与最终 `result` 事件。最终 `data` 固定为四字段：

```json
{
  "schema_version": "1.0",
  "intent": "plan",
  "message": "本轮给用户的简短说明",
  "next_step": {
    "action": "choose_plan",
    "options": [],
    "result": {},
    "invitation": null,
    "selected_plan_id": "路线ID",
    "slots": {},
    "notices": []
  }
}
```

完整结构由 `agent/response.schema.json`、`plan.schema.json` 校验，路线含常住条件、来源渠道状态、费用、时间线、地址、各人往返和邀请函。模型提取另外用 `coordinator.schema.json` 校验；活动供给用 `event-feed.schema.json` 校验。示例文件 `example-request.json` / `example-response.json` 为主动样例请求与真实样例响应，非线上实时推荐。

一个协调模型负责需求提取；程序控制信息源适配、约束计算和邀请函。执行过程展示检索、整合和校验状态，不展示内心推理。不订票、不订位、不支付、不代发消息。

## 降级与数据

模型单次 12 秒、失败重试一次，再降级规则理解；外部信息请求单次 10 秒、并发限制 4；每轮服务端总超时 60 秒。前端超时 75 秒。缺活动信息时保留地图地点及待核实状态，缺地图时不给虚构路线。格式错误、过大输入、超时、无共同时间或无可行路线均可恢复。

定位与对话不写入浏览器持久存储或数据库。会话保留于内存，闲置 30 分钟后在下次请求清理；刷新重新开始。条件发送至配置的模型服务；日常出发地发送至高德；公开搜索只发送城市、片区、日期、兴趣和场馆名，不发送同行人的名字或住宅起点。凭证不进入前端或导出 JSON。

这是单实例 Demo，不含生产用户鉴权、计费与高并发治理。公开推广前应在云网关配置访问配额。预算和交通是估算，源记录日期覆盖出行日仍不保证具体场次、余票、预约与营业，出发前需核对。

## 开发验证

Python 3.12，前端 Node 20+；构建后的 React 已含在包内。开发测试命令：

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r space/requirements.txt
.venv/bin/python -m unittest discover -s tests -v
cd frontend
npm ci
npm run build
```

48 项后端测试覆盖多轮、多城市适配（受控响应）、定位确认、居民通勤与排除、活动驱动候选与费用、来源去重与异城过滤、供给/搜索故障、JSON 校验和会话隔离。另覆盖总预算折算、多人独立时间、无法归属时追问、否定订票表达、具体周日优先和人数上限。桌面和 390px 手机浏览器已验证居住地确认、条件表单、上海供给驱动路线、来源卡、邀请函、城市切换与定位确认；无法明确时间归属时会清除当前可邀请路线。无横向溢出和页面脚本错误。浏览器数据同样使用受控响应。没有使用真实凭证消耗付费配额，不能以模拟验证替代发布后的服务联调。

试运行发现的待改进项：三套路线仍可能重复两站；单一咖啡偏好会被补入餐饮和散步；活动供给只有日级日期，未做具体场次或营业时段校验；通勤仍是直线距离估算；场馆别名匹配需结合 POI ID、地址和坐标。当前适合流程演示，真实活动供给、时段和云端链路仍待联调。

目录依赖方向：`space → service → domain`，`adapters → domain`，`weekend_agent/server.py` 组装依赖。素材来源见 `NOTICE.md`。
